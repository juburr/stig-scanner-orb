# Derive container N/A reasons instead of tailoring

The orb should write its own small, stdlib-only generator that reads OpenSCAP's `results.xml` and emits both a STIG Viewer 2 `.ckl` and a STIG Viewer 3 `.cklb` from one internal model. Rows should be keyed on DISA Vulnerability IDs (V-IDs), with Rule IDs, text and CCIs taken from the DISA manual STIG release that the SSG content was actually built against. The ~400 host-only rules should **stay in the checklist as Not_Applicable rows**, each with a reason derived mechanically from OpenSCAP's own platform evaluation, not from a hand-curated container tailoring file. No existing tool does this conversion correctly. `oscap --stig-viewer` emits zero rule-results on the orb's OpenSCAP 1.3.6 RPM scanner against SSG 0.1.82, and it produces XCCDF results, not a checklist, even when it works. MITRE SAF keys rows on SSG rule IDs that no DISA tool can merge, and Iron Bank, Chainguard and Anchore all stop short of an SSG-to-checklist step. A spike on a real ubi9 scan (62 pass / 8 fail / 406 notapplicable) showed the approach works. The prototype's 445-row checklist against the DISA RHEL 9 V2R9 skeleton came out as 62 NotAFinding / 7 Open / 366 Not_Applicable / 10 Not_Reviewed, STIG Manager's own parsers accept it, and every N/A row has a reason (330 host, 23 GUI, 11 package not installed, 1 generic, 1 check-level) ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). DISA's container guidance explicitly allows documenting non-applicable OS-STIG items as N/A. "Inherited", however, is not a checklist status. STIG Viewer has exactly four, so the wording should say the requirement belongs to the host or platform and must be assessed there, not that it is inherited or met. A tailoring file that deselects host rules would make the evidence worse: deselected rules become `notselected` and show up as unexplained Not Reviewed gaps. The main operational risk is release drift. SSG 0.1.82 is one DISA quarter behind the October 2026 release for every RHEL target, and its Ubuntu profile title names the wrong release, so the release a checklist claims must come from a tested fingerprint.

## Consumers accept both formats but check far less than they appear to

The two formats differ in shape but carry the same data. **CKL** is flat XML: `CHECKLIST > ASSET + STIGS > iSTIG > (STIG_INFO/SI_DATA*) + VULN*`. Each `VULN` holds a run of name/value `STIG_DATA` pairs (`Vuln_Num`, `Rule_ID`, `Rule_Ver`, `CCI_REF`…) followed by five fixed elements: `STATUS`, `FINDING_DETAILS`, `COMMENTS`, `SEVERITY_OVERRIDE` and `SEVERITY_JUSTIFICATION`. Genuine STIG Viewer 2.14 and 2.17 files show the exact element order and values a generator should copy ([MITRE heimdall2 sample checklists](https://github.com/mitre/heimdall2/tree/main/libs/hdf-converters/sample_jsons/checklist_mapper/sample_input_report)). **DISA publishes no stand-alone CKL XSD at a stable URL**, and MITRE's current converter relies on round-trip parsing instead of schema validation for that reason ([mitre/hdf-libs schema_validation_test.go](https://github.com/mitre/hdf-libs/blob/main/hdf-converters/converters/hdf-to-ckl/go/schema_validation_test.go)). STIG Viewer 2.x itself is gone from distribution. On 2026-10-12 DISA's CDN listed only **STIG Viewer 3.8.1** (packages dated 02 Oct 2026), and every historical 2.x download URL returned 404 ([DISA CDN listing](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/)). DISA calls 3.x "a replacement for … STIG Viewer 2.x". 3.x saves CKLB natively but still imports CKL ("Import V2 Checklist") and exports "CKL (SV v2 format)" ([STIG Viewer 3.x User Guide V1R8, 13 Aug 2026](https://dl.dod.cyber.mil/wp-content/uploads/stigs/pdf/U_STIG_Viewer_3-x_User_Guide_V1R8.pdf)). CKL therefore remains the lowest common denominator, and CKLB is the forward format. Both are cheap to emit from one model, so the orb should emit both.

**CKLB** is JSON, and contrary to MITRE's September 2026 notes, DISA *does* publish a schema: `SV3_CKLB_1_0_JSON_SCHEMA.zip` (JSON Schema draft 2019-09, `cklb_version` const `"1.0"`, zip entry dated 2024-01-09) ([DISA CKLB schema](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/SV3_CKLB_1_0_JSON_SCHEMA.zip)). The schema is stale relative to DISA's own tool. Its `additionalProperties:false` rejects `stigs[].version`, `rules[].srg_id` and `target_data.classification`, all of which STIG Viewer 3.7+ writes, so **real STIG Viewer–saved files fail DISA's own schema** (compare a real SV3 RHEL 10 file in [mitre/sv3-runner](https://github.com/mitre/sv3-runner/blob/main/test/fixtures/sample.cklb)). The spike's generated CKLB produced zero errors against a copy of the schema patched to allow those three fields. Against the raw schema, it failed only on `stigs[].version` and `target_data.classification` ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). Dropping `version` would make the raw schema pass, but STIG Manager would then record the wrong revision, so the patched schema is the right CI gate.

What each consumer actually enforces matters more than any schema, and the answer is "very little, sometimes silently":

| Consumer (Oct 2026) | CKL | CKLB | What makes it throw | What it silently drops or mangles |
|---|---|---|---|---|
| STIG Viewer 3.8.1 | Import V2 Checklist; exports CKL | Native; no schema validation on load | VULN missing `Vuln_Num` or `Rule_ID`; missing `title` SI_DATA; fewer than 2 SI_DATA/STIG_DATA children; CKLB with no `stigs` or no per-STIG `rules` array | Unknown STATUS becomes undefined; omitting `SEVERITY_OVERRIDE` creates a bogus override |
| STIG Manager 1.6.17 (parser `stig-manager-client-modules` 1.6.8) | Yes | Yes | Empty `HOST_NAME`/`host_name`; missing `stigid`, `version` or `releaseinfo` SI_DATA; missing `FINDING_DETAILS`/`COMMENTS` elements; CKLB with no `stig_id` | Wrong-case STATUS, missing `Rule_ID` or `rule_id_src` → row dropped; CKLB without `stigs[].version` → revision recorded as `V0R5` |
| eMASS | `disaStigViewerCklCklb` scan type | Same scan type | Not public (CAC-gated docs) | Not public |
| Vulnerator 6.1.9 | Yes | No (issue open since 2023) | n/a | n/a |

Sources: [STIG Viewer 3.8.1 package source](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_STIGViewer-linux-x64-3-8-1.zip); [stig-manager-client-modules 1.6.8](https://registry.npmjs.org/@nuwcdivnpt/stig-manager-client-modules/-/stig-manager-client-modules-1.6.8.tgz); [STIG Manager ReviewsImport.js](https://github.com/NUWCDIVNPT/stig-manager/blob/main/client/src/js/SM/ReviewsImport.js); [eMASS REST OpenAPI](https://github.com/mitre/emass_client/blob/main/docs/eMASSRestOpenApi.yaml); [Vulnerator #232](https://github.com/Vulnerator/Vulnerator/issues/232).

These behaviours set the generator's recipe. For CKL, emit every `ASSET` child in STIG Viewer 2 order. Emit all eleven `SI_DATA` entries, with `releaseinfo` exactly `Release: <n> Benchmark Date: <dd Mon yyyy>`, because STIG Manager computes the revision from that string with a regex. Emit the full `STIG_DATA` sequence per VULN with repeated `CCI_REF`, and always emit the five trailing elements, even when empty. For CKLB, include `cklb_version:"1.0"` (MITRE's converter will not even recognise a file without it ([@mitre/hdf-converters 3.7.2](https://registry.npmjs.org/@mitre/hdf-converters/-/hdf-converters-3.7.2.tgz))), `stigs[].version` as a string, and `rule_id_src` on every rule. STIG Manager keys reviews on `rule_id_src`, and MITRE's own CKLB serializer omits it, so STIG Manager would drop every row that serializer writes ([mitre/hdf-libs cklb.go](https://github.com/mitre/hdf-libs/blob/main/hdf-converters/shared/go/checklist/cklb.go)). Two smaller choices complete the recipe. The CKL header comment should name the orb, as STIG Manager names itself, rather than imitate `<!--DISA STIG Viewer :: 2.18-->`; no consumer reads the comment. The silent drops mean the CI validator must use STIG Manager's parsers *and* assert that row counts and status tallies equal what the generator wrote; "no exception" alone proves nothing. The spike's validator already does this ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). MITRE's `sv3-runner`, which drives the real STIG Viewer 3 under Playwright, shows a true tool-acceptance test is feasible in CI ([mitre/sv3-runner](https://github.com/mitre/sv3-runner/blob/main/README.md)).

The join key everywhere is the **DISA Rule ID** (`SV-257777r925318_rule`), not the V-ID. STIG Viewer 3 first requires an exact `stig_id` match. It then matches rules on the full Rule ID including its revision suffix, and revision-mismatched rows import only if the user ticks "Include loosely matched results" ([SV3 3.8.1 package source](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_STIGViewer-linux-x64-3-8-1.zip); [User Guide V1R8 §5.6](https://dl.dod.cyber.mil/wp-content/uploads/stigs/pdf/U_STIG_Viewer_3-x_User_Guide_V1R8.pdf)). STIG Manager accepts a rule ID found in *any installed revision* of an assigned STIG. It stores reviews under the STIG ID plus a SHA-256 of the check content, so a review carries across revisions only when the check text is unchanged ([STIG Manager review handling](https://github.com/NUWCDIVNPT/stig-manager/blob/main/docs/user-guide/review-handling.rst)). Each file holds exactly one `ASSET`/`target_data`, and STIG Manager matches the asset on `HOST_NAME` exactly. Containers have no hostname, so the orb needs a stable, sanitized image reference (≤255 characters) there, with the digest in `TARGET_COMMENT`. eMASS ingests both formats through `device-scan-results` with `scanType=disaStigViewerCklCklb`. It also exposes a dedicated **`container-scan-results`** API keyed on benchmark ID plus `SV-…_rule`, which is a natural future output for an image scanner ([eMASS REST OpenAPI](https://github.com/mitre/emass_client/blob/main/docs/eMASSRestOpenApi.yaml)). How eMASS validates uploaded checklists is not publicly documented. STIG Viewer 3 and eMASS acceptance therefore remain manual verification steps.

## Every prior-art converter fails on SSG 0.1.82 input

**OpenSCAP's `--stig-viewer`** looks like the obvious mechanism, and it is broken for this orb. It rewrites each rule-result's `idref` to the text of a `<reference>` whose `href` exactly matches a hard-coded list of DISA URLs. OpenSCAP 1.3.6 knows only the `iase.disa.mil` and `public.cyber.mil` hrefs ([OpenSCAP 1.3.6 result.c](https://raw.githubusercontent.com/OpenSCAP/openscap/1.3.6/src/XCCDF/result.c)). SSG switched to `https://www.cyber.mil/stigs/srg-stig-tools/` in v0.1.78 ([CaC v0.1.78 constants.py](https://raw.githubusercontent.com/ComplianceAsCode/content/v0.1.78/ssg/constants.py)), and OpenSCAP added that href only in 1.4.3 and 1.3.13, released November 2025 ([OpenSCAP NEWS](https://raw.githubusercontent.com/OpenSCAP/openscap/main/NEWS)). The spike confirmed the effect. **OpenSCAP 1.3.6, the scanner for every RPM target, writes zero rule-results; 1.4.4 writes 440** ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). Even working output has two problems. It is an XCCDF TestResult whose benchmark id is still the SSG id, which STIG Manager's XCCDF parser rejects outright because it requires the `xccdf_mil.disa.stig_benchmark_` prefix ([stig-manager-client-modules 1.6.8](https://registry.npmjs.org/@nuwcdivnpt/stig-manager-client-modules/-/stig-manager-client-modules-1.6.8.tgz)). And it collapses many-to-one mappings with a rule where "pass" loses to anything, so pass + notapplicable becomes notapplicable, keeping only the first rule's evidence ([OpenSCAP 1.4.4 result.c](https://raw.githubusercontent.com/OpenSCAP/openscap/1.4.4/src/XCCDF/result.c)). Open upstream issues report STIG Viewer, STIG Manager and Heimdall rejecting or showing nothing from this output as recently as February 2026 ([#2240](https://github.com/OpenSCAP/openscap/issues/2240), [#2316](https://github.com/OpenSCAP/openscap/issues/2316), [#2261](https://github.com/OpenSCAP/openscap/issues/2261)).

**MITRE SAF** offers `saf convert xccdf_results2hdf` followed by `hdf2ckl`, and with SSG input that pipeline produces a checklist no DISA tool can merge. `Vuln_Num`, `Rule_ID` and `Rule_Ver` all become the SSG rule id, `Check_Content` is an OVAL definition name, and every `notselected` rule turns into a `Not_Applicable` row. Nothing maps SSG rules to DISA IDs or supplies DISA text or CCIs, and SAF CLI 1.7.0 has no CKLB command ([@mitre/hdf-converters 2.14.0](https://registry.npmjs.org/@mitre/hdf-converters/-/hdf-converters-2.14.0.tgz); [@mitre/saf 1.7.0](https://registry.npmjs.org/@mitre/saf/-/saf-1.7.0.tgz)). Anchore uses this chain, but feeds it InSpec STIG baselines rather than OpenSCAP ([Anchore STIG quickstart](https://docs.anchore.com/current/docs/quickstarts/federalato/stig/)). Two pieces are worth borrowing: MITRE's CKL default constants (weight `10.0`, `Check_Content_Ref` `M`, `Class` `Unclass`) and its machine-parseable FINDING_DETAILS line format, which lets `saf convert ckl2hdf` round-trip a checklist.

**ComplianceAsCode** has no checklist generator, but it owns the mapping the orb needs. At build time `compile_all.py --stig-references` looks each SSG rule's DISA STIG ID up in a vendored DISA manual XCCDF and writes the matching `SV-…_rule` as a `stigref` reference ([CaC v0.1.82 build_yaml.py](https://raw.githubusercontent.com/ComplianceAsCode/content/v0.1.82/ssg/build_yaml.py)). From 0.1.82 it also writes the V-ID as a separate `#vulnerability_id` reference, added because the V-ID is "widely used in the field" ([CaC PR #14820](https://github.com/ComplianceAsCode/content/pull/14820)). CaC **deliberately removed all CCIs in 2025**: per-product CCI assignments diverge, and the project's CCI data was wrong ([CaC ADR 0001](https://complianceascode.readthedocs.io/en/latest/adr/0001_remove_cci.html)). So `results.xml` carries the DISA IDs but no CCIs. The spike also established that `results.xml` is self-sufficient. OpenSCAP writes the full resolved Benchmark, including references and platform gates, ahead of the TestResult, so the generator needs no datastream, no extra container and no network ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)).

The container-focused pipelines confirm the gap rather than fill it. **Iron Bank** scans UBI images with the stock SSG `stig` profile and publishes the raw `--stig-viewer` XCCDF ([ironbank-pipeline oscap_scan.sh](https://repo1.dso.mil/ironbank-tools/ironbank-pipeline/-/blob/master/pipeline1/3-scan/oscap/oscap_scan.sh)). Its tutorial has users build a checklist from the matching DISA STIG in STIG Viewer and import the results into it ([Iron Bank STIG Viewer tutorial](https://p1docs.dso.mil/iron-bank/tutorials/stigviewer)). Only `fail` results become findings in Iron Bank's Vulnerability Assessment Tracker (VAT), keyed by CCE ([openscap_findings.py](https://repo1.dso.mil/ironbank-tools/ironbank-pipeline/-/blob/master/pipeline1/3-scan/openscap_findings.py)). **Chainguard** publishes a GPOS SRG-based datastream whose rule ids *are* DISA GPOS SRG ids (`xccdf_mil.disa.stig_rule_SV-263651r982555_rule`) with CCI idents, plus HTML and XCCDF results, but no checklist ([chainguard-dev/stigs](https://github.com/chainguard-dev/stigs)). That makes the orb's Wolfi path a separate, easier mapping onto a **GPOS SRG** checklist (85 pass / 6 fail / 107 notapplicable against `cgr.dev/chainguard/static` in the spike), not an OS STIG one. **STIG Manager** ingests XCCDF only when the benchmark and rule ids are already DISA-namespaced. No maintained CKL/CKLB library exists on PyPI ([PyPI stig-parser](https://pypi.org/project/stig-parser/)). The orb's generator would be the first open, stdlib-only SSG→CKL/CKLB converter in the surveyed landscape.

### The mapping is many-to-many, so aggregation must be explicit

On RHEL 9, **17 V-IDs are implemented by 2–7 SSG rules each, and 8 SSG rules each cite two or more V-IDs**; for example, `dconf_gnome_disable_restart_shutdown` maps to both V-258029 and V-258030 ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). The generator must pair each `SV-n…_rule` reference with its `V-n` by number rather than take "the" reference. It then reduces all contributing results to one status per V-ID with a rule that deliberately departs from both OpenSCAP (pass loses to N/A) and MITRE (notselected and informational become N/A, which silently closes items):

| Contributing SSG results for one V-ID | CKL / CKLB status | Precedent |
|---|---|---|
| any `fail` | `Open` / `open` | Universal |
| else any `error`, `unknown`, `notchecked`, `informational` | `Not_Reviewed` / `not_reviewed`, saying which | STIG Viewer 3.7+ imports XCCDF error/informational as Not Reviewed ([SV3 3.8.1 release notes](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_STIGViewer-linux-x64-3-8-1.zip)) |
| else all `notapplicable` | `Not_Applicable` / `not_applicable`, with a derived reason | Universal |
| else `pass`/`fixed`, possibly mixed with `notapplicable` | `NotAFinding` / `not_a_finding` | Departs from OpenSCAP's pass-loses rule |
| only `notselected` | ignored; with a DISA skeleton, `Not_Reviewed` "deselected by profile/tailoring" | Departs from MITRE |
| no SSG rule at all (manual-only V-ID) | `Not_Reviewed` / `not_reviewed` | Required for a complete checklist |

The spike's V-258241 row shows why the evidence matters: `configure_crypto_policy` failed while two FIPS sub-policy rules were notapplicable, so the row is Open, and FINDING_DETAILS lists all three ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). No surveyed tool records which SSG rules contributed to a verdict. That list, plus a provenance line (scanner digest, datastream sha256, target digest, scan time), is the most useful thing the orb can add for an assessor.

## DISA's October 2026 release put every pinned STIG one quarter ahead

DISA ships on a **quarterly cadence (January, April, July, October)**. The October 2026 release carries benchmark date 30 Sep 2026, and its files were posted 5–7 October ([DISA CDN listing](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/); [October 2026 library](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_SRG-STIG_Library_October_2026.zip)). SSG 0.1.82 (tagged 2026-09-01) predates that release, and CaC master had not ingested it by 2026-10-12 ([CaC shared/references](https://github.com/ComplianceAsCode/content/tree/master/shared/references)). The spike matched each pinned datastream's `SV-…r…` ids against every DISA release instead of trusting the profile title:

The Ubuntu mislabel has precedent. CaC fixed the same profile in February 2026 after "STIG Viewer imports report V2R3 in the header" while the content was V2R7 ([CaC PR #14459](https://github.com/ComplianceAsCode/content/pull/14459)). A checklist that claims the wrong release breaks row matching in STIG Manager and STIG Viewer, so **the claimed release must come from a fingerprint table that a test checks against the pinned datastream**, not from the profile title. Two oddities need watching. DISA's October library revision history lists `U_RHEL_8_V2R9_STIG.zip` under "Deleted content that has been sunset/removed", even though that zip is downloadable on its own, and DISA gives no explanation ([October 2026 library](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_SRG-STIG_Library_October_2026.zip)). Some non-OS STIGs have also moved from VxRy to year/month versions (`…_Y26M10_STIG.zip`), so revision parsing should not assume VxRy forever.

### Revision suffixes churn, so rows must key on V-IDs

V-IDs are stable: DISA retires them and mints new ones, never reassigns. The `rNNNNNNN` suffix in `SV-…_rule`, by contrast, behaves like a database-wide sequence that DISA bumps in bulk. Between RHEL 9 V2R9 and V2R10, **206 of 443 surviving rules got a new SV id, and 153 of those changed nothing visible** in title, discussion, check, fix, severity or CCIs. The 143 rules sharing `r1268251` all sit under one SRG, and many V2R10 bumps are just the DoD→DoW rename ([RHEL 9 V2R9](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R9_STIG.zip) vs [V2R10](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R10_STIG.zip)). DISA acknowledges id-only churn, rebundling one benchmark "to capture Rule ID revision bumps" ([April 2026 STIGs to be Released](https://dl.dod.cyber.mil/wp-content/uploads/stigs/pdf/April%202026%20STIGs%20to%20be%20Released.pdf)). DISA's own files also disagree within a single release. Only **237 of 393 SV ids in the V2R10 SCAP benchmark** match the V2R10 manual, though all 393 V-IDs do ([RHEL 9 V2R10 SCAP benchmark](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R10_STIG_SCAP_1-3_Benchmark.zip)). The design follows directly. Join SSG results to the DISA skeleton on V-ID. Write the skeleton's own Rule ID into each row, and record the SSG-aligned SV id in FINDING_DETAILS. When the skeleton is newer than the content, carry a result forward only where the check text is unchanged and mark the rest Not_Reviewed, which mirrors STIG Manager's check-content hashing. That comparison needs the content-matched release's check text. Without it, every revision-mismatched row should be Not_Reviewed, keeping the older result as evidence rather than as the verdict (revised in PR review). Raise release-mismatch warnings by comparing benchmark id plus version/release, never individual revisions. By default the skeleton should be the fingerprinted release; with that skeleton the spike saw zero revision mismatches, against 200 on V2R10 ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)).

DISA's SCAP benchmark is not a substitute skeleton. It covers only the automated subset (**393 of 445** RHEL 9 rules), its revisions disagree with the manual, and its 23 `systemdunitproperty` tests are unlikely to mean anything under `oscap-chroot` against an extracted rootfs. The manual XCCDF is the right source.

### CCIs must come from each STIG's own idents

`CCI_REF` is the field eMASS and STIG Manager use to roll checklist rows up to NIST 800-53 controls, and SSG cannot supply it. Every rule in every current DISA OS STIG carries at least one `<ident system="http://cyber.mil/cci">`, and **164 of 445 RHEL 9 V2R10 rules carry more than one** ([RHEL 9 V2R10](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R10_STIG.zip)). Deriving CCIs from a rule's SRG through the GPOS SRG is tempting but lossy. It reproduces a STIG's own CCI set exactly for only **60% of RHEL 9 rules, 63% of RHEL 10, 71% of Ubuntu 22.04 and 89% of RHEL 8** ([GPOS SRG V3R4](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_GPOS_V3R4_SRG.zip)). CCIs must therefore come from the matching DISA manual STIG. The authoritative CCI list, needed only to render CCI → NIST mappings, is `CCI_List.zip` version **2026-07-14** (5,149 items). A stale `U_CCI_List.zip` (2025-01-23) is still served beside it, so pin by sha256 rather than by name ([CCI_List.zip](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/CCI_List.zip); [U_CCI_List.zip](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_CCI_List.zip)). Without DISA data, an SSG-only checklist has empty CCI fields, SSG wording and no manual-only rows. It is useful, but visibly incomplete.

### DISA data downloads anonymously but carries no stated license

Every STIG zip, quarterly library and CCI list downloads over plain HTTPS from `dl.dod.cyber.mil` with no CAC or login. The server exposes an open directory index of 1,035 files that works as a de facto catalog. It also honours HTTP Range, so a client can pull one member out of the 376 MB October library without downloading the whole thing ([DISA CDN listing](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/)). There is no API or feed. The `www.cyber.mil` front end is a JavaScript-rendered Salesforce page, its `/stigs/feed/` returns a login portal, and the directory index is undocumented and could disappear. URL patterns are predictable (`U_RHEL_9_V2R10_STIG.zip` → `U_RHEL_9_V2R10_Manual_STIG/U_RHEL_9_STIG_V2R10_Manual-xccdf.xml`). Old releases are kept inconsistently. RHEL 9 V2R4 through V2R10 all download, but the standalone Ubuntu 22.04 V2R9 zip, the Ubuntu 24.04 V1R1–V1R6 manual zips and GPOS SRG V3R3 all return 404. A pin therefore needs its own retained copy plus a sha256, never a runtime fetch. Runtime fetching would also break the orb's promise that a scan's only egress is image pulls.

Size is not the constraint. A manual XCCDF is about 1.4 MB raw and 132 KB gzipped for RHEL 9 ([RHEL 9 V2R10](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R10_STIG.zip)). The spike measured compact per-STIG data at about 150 KB, and a V-ID → CCI map at 2.7 KB gzip+base64, both well under the 8 MB packed-orb limit ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). The constraint is legal clarity. **No October 2026 file carries a Distribution Statement or license.** A search of every PDF in the downloaded zips found zero hits for "Distribution Statement", "approved for public release" or "distribution is unlimited", and the XCCDF `terms-of-use` notice is empty. The Overview says "other agencies and organizations are free to use it" without addressing redistribution ([RHEL 9 V2R10](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_RHEL_9_V2R10_STIG.zip)). The US-government-work exemption ([17 U.S.C. §105](https://www.law.cornell.edu/uscode/text/17/105)) does not cleanly cover the RHEL and Ubuntu STIGs either, because their covers read "Developed by Red Hat and DISA" and "Developed by Canonical Ltd. and DISA". The precedent is strong all the same. **ComplianceAsCode, under BSD-3-Clause, has committed DISA manual and SCAP XCCDFs and the CCI list to its repository for years**; its RHEL 9 V2R9 copy is byte-identical to DISA's apart from whitespace ([CaC shared/references](https://github.com/ComplianceAsCode/content/tree/master/shared/references); [CaC LICENSE](https://github.com/ComplianceAsCode/content/blob/master/LICENSE)). STIG Manager takes the opposite route and has admins download STIGs from DISA and upload them ([STIG Manager admin quickstart](https://github.com/NUWCDIVNPT/stig-manager/blob/main/docs/admin-guide/admin-quickstart.rst)). Every checklist DISA's own tool writes embeds the full rule text, so checklists inherently redistribute DISA wording. The defensible sequence is therefore: accept a user-supplied DISA zip or XCCDF first, since that sidesteps the question and satisfies users who must use "the copy from cyber.mil". Then bundle data for the fingerprinted releases only after a maintainer sign-off, with source URLs and sha256s recorded in provenance. A compact JSON extract is a *derived* file, unlike CaC's verbatim copies, and that sign-off should cover it explicitly.

## Host-only rules belong in the checklist as Not_Applicable with derived reasons

DISA's most specific statement is the **Container Hardening Process Guide V1R2 (24 August 2022)**, the newest release found. Appendix B: "Many of these STIGs were designed prior to the existence of containers. If a specific hardening recommendation does not make sense for a container … **it is accepted to document these as nonapplicable**." Appendix D adds that "many of the base OS STIG requirements are not applicable in the containers", and that for false positives or non-applicable items one may "modify scanning profiles to mark specific components as nonapplicable" ([Container Hardening Process Guide V1R2](https://dl.dod.cyber.mil/wp-content/uploads/devsecops/pdf/Final_DevSecOps_Enterprise_Container_Hardening_Guide_1.2.pdf)). The older Container Image Creation and Deployment Guide (V2R0.6, November 2020) said such exceptions needed an approved **waiver** ([CICDG V2R0.6](https://dl.dod.cyber.mil/wp-content/uploads/devsecops/pdf/DevSecOps_Enterprise_Container_Image_Creation_and_Deployment_Guide_2.6-Public-Release.pdf)). An ISSM could cite either, so the orb's documentation should cite V1R2 by appendix and acknowledge that acceptance is site-specific. The STIG itself offers no container clause: none of the 445 RHEL 9 V2R9 check texts mentions containers. It does offer DISA's own N/A phrasing for absent features. **23 rules say "If the system does not have any graphical user interface installed, this requirement is Not Applicable"**, and V-257879 makes data-at-rest encryption N/A when "a documented and approved reason" places it at a hypervisor or storage layer ([DISA RHEL 9 STIG V2R9](https://github.com/ComplianceAsCode/content/blob/master/shared/references/disa-stig-rhel9-v2r9-xccdf-manual.xml)). DISA has never published a container-image STIG or SRG; its container content targets platforms (Container Platform SRG V2R5, Kubernetes STIG V2R6) ([Container Platform SRG V2R5](https://dl.dod.cyber.mil/wp-content/uploads/stigs/zip/U_Container_Platform_V2R5_SRG.zip)).

### "Inherited" is RMF vocabulary, not a checklist status

DISA's guide does use the word, architecturally: "containers inherit most of the security controls … from infrastructure to host OS-level remediation requirements" (Appendix C). Chainguard's rationales follow suit ("Linux containers inherit the firewall configuration of their host operating system") ([Chainguard Academy](https://edu.chainguard.dev/chainguard/containers/security-and-compliance/stigs/)). In RMF, though, **inheritance is a control-level relationship**: protection from controls "developed, implemented, assessed, authorized, and monitored by entities other than those responsible for the system" ([NIST glossary](https://csrc.nist.gov/glossary/term/control_inheritance)). eMASS records it per *control* as `Inherited` or `Manually Inherited`, the latter with a named common control provider ([eMASS REST OpenAPI](https://github.com/mitre/emass_client/blob/main/docs/eMASSRestOpenApi.yaml)). A STIG checklist has exactly four statuses: Open, Not A Finding, Not Applicable and Not Reviewed ([User Guide V1R8](https://dl.dod.cyber.mil/wp-content/uploads/stigs/pdf/U_STIG_Viewer_3-x_User_Guide_V1R8.pdf)). "Inherited" therefore cannot be a status. As a comment, it is accurate only if the host or platform really is a common control provider in that system's eMASS record, and an image scanner cannot know that. Iron Bank states plainly that hardened containers carry no ATO and that the consuming program must assess them ([Iron Bank overview](https://docs-ironbank.dso.mil/overview/)).

The other two statuses are wrong for the same reason. NotAFinding would assert that this target meets the check, which the scanner never verified for the host. Not_Applicable says the requirement is out of scope for this target, and that is what DISA's guide prescribes. DISA itself is inconsistent at the margins: three RHEL 9 USBGuard rules call a VM with no USB peripherals "not a finding", while a fourth calls it "Not Applicable". That is not a reason to pick NotAFinding. Field practice agrees. MITRE's container-aware RHEL 9 InSpec baseline marks **184 controls "This control is Not Applicable to containers"**, sometimes adding "the containers host manages the containers filesystems" ([mitre/redhat-enterprise-linux-9-stig-baseline](https://github.com/mitre/redhat-enterprise-linux-9-stig-baseline)). Iron Bank's parser counts `notapplicable` as passing, and its FAQ describes failing host-only items justified as **"Does Not Apply"** ([Iron Bank oscap parser](https://repo1.dso.mil/ironbank-tools/ironbank-pipeline/-/blob/master/ironbank/pipeline/scan_report_parsers/oscap.py); [Iron Bank FAQ](https://docs-ironbank.dso.mil/faq/)). The right pattern is **Status = Not_Applicable** with a comment saying the requirement is the responsibility of the container host or platform and is assessed on that host's checklist. The wording should be conditional and should never claim the control is met. Sites whose host really is a common control provider can switch to "inherited from [provider]" through an override template.

### OpenSCAP already knows why each rule was N/A

The justification can be evidence rather than assertion, because SSG encodes container applicability in platform gates. Since **SSG v0.1.75 (November 2024)** most host-only rules are gated on `system_with_kernel`, which is true only when the `kernel-core` RPM is installed. A classic container image does not ship a kernel, so the gate is false ([CaC system_with_kernel.yml](https://github.com/ComplianceAsCode/content/blob/master/shared/applicability/system_with_kernel.yml)). A smaller set uses `container`, `machine` or `not_bootc_and_not_container`, which test for `/.dockerenv` or `/run/.containerenv` in the scanned root ([CaC container.yml](https://github.com/ComplianceAsCode/content/blob/master/shared/applicability/container.yml)). Gates sit on groups as well as rules: auditing, SELinux and logging groups carry `system_with_kernel`, and the partitioning groups carry `not container and not bootc` ([CaC linux_os/guide](https://github.com/ComplianceAsCode/content/tree/master/linux_os/guide)). Comparing each rule's gates with the TestResult's list of true platforms tells the generator *why* a rule was notapplicable, with no hand-maintained list of ~400 host rules ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)).

The spike caught a trap that would have put false statements in assessor evidence. **OpenSCAP evaluates applicability from the outermost group inward and stops at the first false gate**, so the TestResult lists only gates it actually evaluated. A rule-first walk blamed `package_shadow-utils` and `package_libpwquality` for 17 ubi9 rules. Both packages are installed; the real cause was the enclosing group's `system_with_kernel`. Walking from the outermost group to the rule fixes this, and fixture tests must pin that behaviour ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). With that walk, the 366 Not_Applicable RHEL 9 rows split cleanly into categories that each get fixed wording:

| Category (ubi9 count) | Trigger: outermost unmet gate | COMMENTS (draft) | Official anchor |

COMMENTS carries the short human reason. FINDING_DETAILS carries the machine evidence: each contributing SSG rule, its result, the unmet gate, and the provenance line. Three boundaries keep this honest. First, **never auto-convert a `fail` to N/A**. DISA's guide requires evaluating each failing result, and Iron Bank routes those to human reviewers ([Iron Bank justifications](https://docs-ironbank.dso.mil/hardening/justifications/)). Second, never use "package not installed" for a rule whose requirement *is* to install the package. SSG kernel-gates those (audit, AIDE, openssh-server), so they land in the host category. Third, the nine manual-only rows in RHEL 9 V2R9, such as V-257782 (hardware RNG entropy gatherer), can only be Not_Reviewed automatically. A small opt-in answer set for the plainly host-level ones is the one piece of hand-maintained container content that earns its keep. None of this wording has been validated by an ISSM, and no source names a phrase that assessors "accept". The defaults need a customer ISSM's review, and they should be overridable.

## Tailoring away host rules turns evidence into Not Reviewed gaps

A container-tailored STIG tailoring file sounds like the tidy answer, and DISA's "modify scanning profiles to mark specific components as nonapplicable" can be read as endorsing one. The strongest case for it is a smaller report with only container-relevant rows. XCCDF semantics defeat it. **A tailoring file cannot produce `notapplicable`.** It can deselect a rule, whose "result becomes notselected", or set its role to unchecked, whose result becomes `notchecked`. `notapplicable` comes only from a platform that does not match ([NISTIR 7275 Rev. 4, XCCDF 1.2](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir7275r4.pdf)). Red Hat's documentation says OpenSCAP "does not evaluate" a not-selected rule, so its result carries no evidence, and a checklist generator has nothing to report for it ([RHEL 9 Security Hardening, ch. 7](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/security_hardening/scanning-the-system-for-configuration-compliance-and-vulnerabilities_security-hardening)). STIG Viewer imports update only the rules they match by Rule ID, so every deselected DISA rule stays **Not Reviewed**, which an assessor reads as incomplete ([User Guide V1R8 §5.6.1](https://dl.dod.cyber.mil/wp-content/uploads/stigs/pdf/U_STIG_Viewer_3-x_User_Guide_V1R8.pdf)). In an SSG-only checklist those rows vanish entirely. With a DISA skeleton they look like rules with no automated check, which is false ([spike, docs/planning/stig-checklist/spike.md](../stig-checklist/spike.md)). Either way, the assessor loses the machine-generated proof that each host rule was considered and why it did not apply. "Mark as nonapplicable" means keep the row and change its status, not remove it.

Nobody upstream ships such a file, either. Red Hat's guidance runs the stock profile against images and notes that notapplicable rules "apply only to bare-metal and virtualized systems" ([RHEL 9 Security Hardening, ch. 7](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/security_hardening/scanning-the-system-for-configuration-compliance-and-vulnerabilities_security-hardening)). SSG's RHEL 9 `stig` profile description already lists "Red Hat Containers with a Red Hat Enterprise Linux 9 image" ([CaC rhel9 profiles](https://github.com/ComplianceAsCode/content/tree/master/products/rhel9/profiles)). Iron Bank scans with the unmodified `content_profile_stig`; its only modification is a one-rule deselection for Amazon Linux 2023 ([ironbank-pipeline set_oscap_profile.py](https://repo1.dso.mil/ironbank-tools/ironbank-pipeline/-/blob/master/pipeline1/3-scan/oscap/set_oscap_profile.py)). Chainguard keeps all 198 GPOS rules *selected* and makes 107 of them N/A through a never-matching platform (`cpe:/o:notapplicable`) with a per-rule rationale citing the DISA guide ([chainguard-dev/stigs](https://github.com/chainguard-dev/stigs)). That is the SCAP-native way to put a justification in content, but it requires editing the benchmark, which a tailoring file cannot do. The orb achieves the same result in its checklist renderer instead: the row stays, the status is Not_Applicable, and the rationale goes in COMMENTS.

Tailoring still has a legitimate job: refining variable values and adding rules for the ungated or package-present rules that *do* evaluate on a container. The orb should therefore ship **no** deselecting container tailoring file, offer a `tailoring_file` passthrough, and have the generator label "deselected by tailoring `<profile>`" separately from "no automated check". The README should tell users not to deselect host rules to clean up the report, because the checklist already explains them.

Derived justifications have pitfalls of their own, and each one argues for keying the reason off the actual result and gate, never off "it's a container". First, **`rootfs_path` trees can lack `/.dockerenv`**. Docker creates the file in the container's init layer, and the orb's `docker export` includes it (verified on Docker 29.8.2), but `umoci`, `crane export` or a VM tree will not. In that case the partitioning, mount-option, sniffer and wireless rules (about 35 in the RHEL 9 profile, counted locally against the pinned datastream from the gates in [CaC linux_os/guide](https://github.com/ComplianceAsCode/content/tree/master/linux_os/guide)) become applicable and likely fail. Second, an image that installs `kernel-core` turns `system_with_kernel` true and brings ~350 host rules into scope. For bootc images that is correct, because they are OS images ([CaC bootc.yml](https://github.com/ComplianceAsCode/content/blob/master/shared/applicability/bootc.yml)); for a driver-build image, those are real failures that must not be relabelled. Third, `system_with_kernel` is an rpminfo test. A scanner without librpm collapses every gated rule to N/A, the signature reported in [OpenSCAP #2278](https://github.com/OpenSCAP/openscap/issues/2278), so "all N/A" is a scanner defect, not a container verdict. The orb's zero-evaluated-rules gate already catches it. Fourth, architecture gates read `/proc/sys/kernel/osrelease`, which reflects the scanning host ([CaC not_aarch64_arch.yml](https://github.com/ComplianceAsCode/content/blob/master/shared/applicability/not_aarch64_arch.yml)). Any architecture justification should cite the image platform recorded in provenance instead.

## Conclusion

The difficult part of this feature is not the file format. Both formats are a few hundred lines of stdlib serialization, and STIG Manager's parsers make a cheap, strict CI oracle once row counts are asserted. The difficult part is *provenance of truth*: which DISA release the content really targets, which DISA rule each SSG result answers, and why each rule did not apply. Every surveyed tool gets at least one of these wrong. OpenSCAP trusts an href list, MITRE trusts SSG ids, SSG's own profile title mislabels Ubuntu, and a hand-made tailoring file would replace "why" with silence. Deriving all three from data the scan already produced turns the checklist from a form an ISSM fills in into a reproducible evidence artifact. Human judgment remains for three narrow cases: approving the default wording, answering the handful of manual-only rows (nine for RHEL 9 V2R9), and reviewing genuine failures. The N/A justification and the orb's existing hollow-scan gate turn out to be two halves of one guarantee. One explains every legitimate N/A, and the other refuses to let a scanner defect hide behind them.

Two obligations follow. Release drift is now a quarterly maintenance cost tied to pin bumps: each DISA release moves the target, and the fingerprint test is what makes the drift visible instead of silently wrong. Three things also remain unproven: real STIG Viewer 3 and eMASS imports, assessor acceptance of the default wording, and a maintainer decision on redistributing DISA text. Until those are settled, the safe defaults are an SSG-only checklist plus a user-supplied DISA file, with bundled DISA data held back.
